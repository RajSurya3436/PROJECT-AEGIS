# Evaluation set

Seven synthetic incidents with a known ground truth, to measure two things a demo cannot:
whether detection fires exactly as intended, and whether the agents' verdict agrees with what
really happened — including when the honest answer is "benign" or "can't tell".

- Scenarios: `data/eval/scenarios.json` and `data/eval/scenarios/*.jsonl`, generated by
  `scripts/make_eval_set.py` (a test keeps them in sync). RFC 5737 documentation IPs only.
- Runner: `app/evaluation/runner.py`; CLI: `scripts/run_eval.py` (`--detection-only` needs no
  model and takes seconds; `--only <id> ...` runs a subset). Results go to
  `data/eval/results/<UTC time>.md|.json` (git-ignored, machine-specific).
- Each scenario runs in its own in-memory database with the demo IOC list loaded and external
  lookups off; the agents start from the alert listed for the scenario with no analyst
  instruction.

## Scenarios

| ID | Ground truth | What happened | Expected alerts |
|---|---|---|---|
| s1_stolen_password_payload | malicious | VPN password guessed; minutes later hidden encoded PowerShell downloads from the IOC server and runs discovery | failures-then-success, repeated failures, PowerShell, IOC connection |
| s2_mistyped_password | benign | three typos at the user's own desk, usual time and IP, then normal mail/Teams use | failures-then-success |
| s3_deployment_powershell | benign | the deployment agent (`ccmexec.exe`) runs the same encoded update script every night | PowerShell ×6 |
| s4_password_spray | malicious | one external IP tries eight accounts; nothing succeeds | password spray |
| s5_lone_ioc_hit | undetermined | one connection to a listed IOC; no process or logon telemetry for the host | IOC connection |
| s6_wazuh_ssh_backdoor_user | malicious | (Wazuh alerts) SSH brute force, login, then a UID 0 account created | failures-then-success, repeated failures, Wazuh high-level |
| s7_unfamiliar_ip_login | undetermined | four failures then a success from an unfamiliar external IP; nothing after | failures-then-success |

## Grading

| Ground truth | correct | cautious (safe, costs analyst time) | wrong (dangerous) |
|---|---|---|---|
| malicious | likely/confirmed malicious | suspicious_inconclusive, insufficient_data | benign (missed attack) |
| benign | benign_or_expected | suspicious_inconclusive, insufficient_data | likely/confirmed malicious (false accusation) |
| undetermined | suspicious_inconclusive, insufficient_data | — | any confident verdict (overconfident) |

*Agreement* is correct ÷ completed runs. The number to watch first is *wrong*: an analyst
copilot that hedges wastes time, one that is confidently wrong does harm.

## Results with `qwen3:8b` (8 GB GPU, 16k context)

### Baseline (2026-10-30)

| | |
|---|---|
| Detection as expected | 7 of 7 |
| Verdicts | 2 correct, 5 cautious, **0 wrong** |
| Agreement | 29% |
| Time per alert | median 96 s, max 165 s |

The verifier answered `suspicious_inconclusive` in every scenario. No deterministic check
changed a verdict; the model chose it. Its rationales showed two causes:

1. The prompt said to hedge when "missing key telemetry", and every realistic case has some gap
   (a VPN gateway never has process logs), so it always did.
2. A defect: a provider *skipping* a private or documentation address was recorded as missing
   telemetry, and the model cited it as doubt. Skipping such addresses is by design, not a gap.

Fixes: skipped lookups are no longer recorded as gaps (the tool tells the agent why nothing
was sent), and the verifier prompt now says when to commit to a verdict in either direction and
that a gap only matters if it would change the conclusion. The guidance is general SOC
reasoning, not keyed to these scenarios.

### After the fixes (2026-10-31)

| | Baseline | After |
|---|---|---|
| Detection as expected | 7 of 7 | 7 of 7 |
| Verdicts | 2 correct, 5 cautious, 0 wrong | 4 correct, 3 cautious, **0 wrong** |
| Agreement | 29% | 57% |
| Time per alert | median 96 s, max 165 s | median 80 s, max 112 s |

| Scenario | Truth | Verdict | Grade |
|---|---|---|---|
| s1_stolen_password_payload | malicious | likely_malicious | correct |
| s2_mistyped_password | benign | benign_or_expected | correct |
| s3_deployment_powershell | benign | suspicious_inconclusive | cautious |
| s4_password_spray | malicious | suspicious_inconclusive | cautious |
| s5_lone_ioc_hit | undetermined | suspicious_inconclusive | correct |
| s6_wazuh_ssh_backdoor_user | malicious | suspicious_inconclusive | cautious |
| s7_unfamiliar_ip_login | undetermined | suspicious_inconclusive | correct |

The model now commits in both directions (s1 malicious, s2 benign) and still hedges on the two
cases built to be undecidable, so the prompt change did not make it overconfident. One run per
scenario; a local 8B model is not deterministic, so a single scenario can flip between runs.

Why the three remaining cases hedged (from the verifier's rationale):

- **s4 password spray**: the model treated "malicious" as "compromised". Eight accounts tried
  from one external address is an attack whether or not it succeeded; it hedged because there
  was no process or network telemetry from the VPN gateway, which could not change that.
- **s6 Wazuh backdoor user**: the run started from the failures-then-success alert, and the
  specialists made 3 tool calls and recorded no evidence. They never looked at the related Wazuh
  high-level alert for the UID 0 account, which is what makes the case clear. This is depth of
  investigation, not verifier judgement.
- **s3 deployment PowerShell**: it saw "encoded command" and stopped; it did not weigh the
  parent process (`ccmexec.exe`), the service account, or that the same command runs every night.

Possible next improvements (not done): tell the log investigator to check other alerts on the
same host/user before finishing, and tell the verifier that an attack attempt is malicious even
without evidence of success.
